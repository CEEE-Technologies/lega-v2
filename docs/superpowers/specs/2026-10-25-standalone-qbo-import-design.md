# Standalone QBO extraction for lega-v2

Date: 2026-10-25
Status: Approved by the user and implemented. Automated verification: 32 tests passing on Node 18.20.8; live QBO authorization remains an operator step.

## Intent and agreed choices

Provide a standalone tool inside the lega-v2 repository that connects directly to QuickBooks Online, captures its standard accounting data, and saves it for a later lega-v2 import. The user selected a CLI with browser sign-in. Extraction and applying data to a lega-v2 company are separate operations; this project delivers extraction and an explicit, documented bundle contract for that later importer.

The tool must run without the lega-v2 API, MariaDB, Redis, or the original LEGA checkout. It must retain source fields and relationships, including data the current lega-v2 application cannot represent yet.

## Approaches

1. **Standalone CLI with browser sign-in (selected):** small operational footprint, local files, scriptable and resumable. Operators run commands and review a summary in the terminal.
2. **Separate local web app:** friendlier progress screens but adds a frontend/server to operate. The user chose the CLI.

Reusing the original LEGA NestJS migration module directly is unsuitable: its staging, leases, auditing, and apply services depend on MongoDB and the original accounting application. Port its independent client and extraction behavior instead.

## Deliverables and boundaries

- New workspace package `packages/qbo-import`, provisionally named `@lega/qbo-import`, with its own README, build, test, and typecheck scripts.
- Root `qbo:import` command; proposed usage after building the package:

  ```sh
  pnpm qbo:import connect
  pnpm qbo:import extract --out ./qbo-data/company-backup
  pnpm qbo:import status --out ./qbo-data/company-backup
  pnpm qbo:import resume --out ./qbo-data/company-backup
  pnpm qbo:import validate --out ./qbo-data/company-backup
  pnpm qbo:import disconnect
  ```

- Node 18 compatible TypeScript, following the repository's pnpm workspace conventions. Use Node built-ins where practical; do not bootstrap the NestJS server.
- Read QBO accounting resources only. No QBO entity writes, no lega-v2 tenant writes, no database migrations, no posting or balance conversion.
- CSV/XLSX ingestion, application UI, and the later lega-v2 apply adapter are outside this implementation.
- Do not describe the resulting JSON bundle as directly uploadable to lega-v2's current CSV/XLSX importer. That importer uses resource metadata and destination-specific mappings.

## Source coverage

The baseline follows LEGA's extraction catalog:

- CompanyInfo, Preferences.
- Account, Class, Department, Term, TaxAgency, TaxRate, TaxCode, PaymentMethod, Customer, Vendor, Item.
- Invoice, CreditMemo, SalesReceipt, RefundReceipt, Payment, Deposit, Bill, BillPayment, VendorCredit, Purchase, Transfer, JournalEntry.

Proposed extension for the user's broad preservation goal: also extract Estimate, PurchaseOrder, TimeActivity, Employee, and Attachable metadata when available through the standard Accounting API. These are retained as source records even if a future lega-v2 mapper does not support them. Verify entity query/filter support against Intuit's documentation during implementation. Do not silently expand into payroll, payments processing, or premium APIs. Binary attachment downloads are outside this first version; retain metadata and source links and state this limitation in the bundle.

Required versus optional (implementation proposal following LEGA): Class, Department, Term, TaxAgency, TaxRate, TaxCode, PaymentMethod, RefundReceipt, VendorCredit, and Transfer are optional; the five extensions are also optional. Every other baseline entity is required. An empty successful query is a completed resource with zero records. An optional resource can be unavailable only after a documented unsupported/permission response; a required resource's permission failure stops extraction. Every report generated by the report plan is required. When no inventory accounts exist, no GeneralLedger requests are planned; that is recorded as not applicable rather than unavailable.

Fetch active and inactive masters where supported. Preserve every returned field, nested line, reference, currency, tax, metadata, and source ID without case conversion, rounding, or flattening. No date filter on entity extraction: capture the available history. This does not promise deleted records or data QBO does not expose.

Preserve reconciliation reports using LEGA's plan: accrual BalanceSheet, TrialBalance, and ProfitAndLoss per fiscal year through extraction cutover; AgedReceivables and AgedPayables at cutover; GeneralLedger for inventory assets, cost of goods sold, and opening balance equity per fiscal year when inventory exists. Determine fiscal year from CompanyInfo; use a documented January fallback when absent. Default cutover is today's date in Asia/Colombo or the latest extracted transaction date, whichever is later; allow an explicit report date. This date controls reports, not an exclusion of source transactions.

## Connection and credentials

- Load the canonical root `.env`, with process environment taking precedence. Document `QBO_CLIENT_ID`, `QBO_CLIENT_SECRET`, `QBO_ENVIRONMENT`, `QBO_REDIRECT_URI`, and `QBO_TOKEN_KEY`; keep real credentials out of arguments, examples, and output.
- Request only the standard accounting scope. Generate random single-use OAuth state, validate it, expire it after ten minutes, and reject replay or realm changes during a run.
- Sandbox: temporary loopback HTTP callback listener; open the browser and print the authorization URL as a fallback. Bind the listener to loopback, close it on success, cancellation, or timeout.
- Production: Intuit requires a registered HTTPS redirect URI. Support browser sign-in with manual completion by pasting the complete redirected URL into a hidden terminal prompt. The CLI validates state and exchanges the code with the same configured redirect URI. A callback page must avoid logging or forwarding codes; no hosted callback infrastructure is provisioned by this project. Explain setup and the manual workflow in the README.
- Store encrypted tokens outside the export bundle in a private local state directory, using AES-256-GCM and the configured token key, with restrictive permissions. Store refresh-token rotations atomically before continuing. Serialize token refreshes and lock connection state against concurrent processes.
- Never print access/refresh tokens, client secrets, pasted callback URLs, or raw authentication errors. Connection status may show environment, realm, company, and expiry.
- `disconnect` revokes the connection when possible and removes local tokens. It never deletes saved bundles.

Intuit's own CLI documents the sandbox/production redirect distinction: https://github.com/intuit/intuit-cli-for-quickbooks#prerequisites .

## Bundle contract (version 1)

The output directory is portable and independent of credentials:

```text
manifest.json
entities/<Entity>/pages/<start-position>.json
reports/<stable-report-id>.json
```

Each entity page contains an array of untouched QBO objects. CompanyInfo and Preferences use one-element arrays. Reports retain the complete API report JSON. File names come only from the internal entity catalog and safe generated report identifiers, never source names or caller-supplied paths.

`manifest.json` contains format name `lega-qbo-bundle`, version `1`, run ID, QBO environment and realm, company name and home currency, API minor version, start/update/completion timestamps, extraction state, coverage catalog, and source limitations. Each entity lists status, next position, record count, and committed page paths/counts/SHA-256 hashes. Each report includes its request name, exact parameters, purpose, date range, path, and checksum. Warnings distinguish unavailable resources, unsupported inactive filters, missing metadata, and incomplete extraction. No secrets or temporary signed attachment URLs are deliberately added to metadata; raw records remain raw data.

`validate` checks version, schema, file containment, checksums, counts, expected files, unique source IDs per entity, and required completed resources without calling QBO. It rejects malformed or corrupted bundles and unsupported versions. A later importer must validate first and resolve references by `(realmId, entity, sourceId)`, rather than relying on display names or destination IDs. Provide a documented bundle reader or exported types/validation API for that importer.

Local state/output directories are ignored by Git. Create private output directories and files by default because they contain company data. Do not include live QBO fixtures in tests.

## Extraction, restart, and failure behavior

- Pin environment and realm to the run; resume checks they match the active connection and the bundle version/configuration.
- Save each page atomically, then atomically update the manifest cursor. A crash before the manifest update re-fetches and replaces the same page. Completed pages are verified before resuming.
- Permit one writer per bundle and one token refresher per connection. Define stale-lock recovery explicitly and avoid allowing an interrupted process to overwrite another active writer.
- Port LEGA's pagination, bounded retries, backoff, Retry-After handling, and one refresh on HTTP 401. Pin a supported API minor version and record it in every bundle. Add request timeouts and cancellation cleanup.
- Required entity failures stop extraction, preserve completed work, set a failure summary, and exit nonzero. Optional resources may be marked unavailable only for documented unsupported/permission responses; warn visibly and retain the reason. Never treat malformed responses, auth failures, or transient server errors as an empty entity.
- Reports that cannot be fetched remain incomplete and resumable and stop completion; never fabricate zero balances. Completion summaries show scope and warnings. A complete bundle may contain explicitly unavailable optional entities; it must contain every required entity and planned report. The later importer must inspect those coverage warnings before applying anything.
- Validation never claims QBO was unchanged during extraction. QBO's independent paginated API requests do not provide a database snapshot; record run timing and warn operators to avoid source edits while extracting. Resuming captures the remaining pages, not a historical point-in-time snapshot.
- Do not overwrite an existing run with `extract`; use `resume` or a new output directory.

## Verification and acceptance

Use synthetic QBO responses and a fake local HTTP server; do not require real company credentials for automated checks. Cover browser callback state/expiry/replay and manual callback completion; refresh rotation and secret redaction; multi-page and inactive-resource extraction; optional-resource warnings versus fatal errors; interrupted page/manifest writes and resume; realm/environment mismatch; report planning; bundle corruption/duplicate IDs/path escape checks; and concurrent writers.

Acceptance: from a fresh CLI process with no lega-v2 services running, connect to a fake QBO endpoint, extract a multi-page company to a bundle, interrupt/resume it, and validate the result without network access. Run package tests, typecheck, and build under Node 18. A real QBO smoke test requires the operator's Intuit credentials and interactive authorization and must be reported separately from automated verification.

## Decisions left to implementation

CLI argument library, minimal runtime validation library, internal module boundaries, lock implementation, exact output rendering, and test runner are implementation choices. Prefer dependencies already available in the repository. Preserve existing uncommitted work and avoid editing unrelated branding/application files.

## Design review

A fresh builder review identified one material ambiguity: required versus optional source coverage. The explicit policy above resolves it using LEGA's existing optional entity catalog, conditional extensions, and required planned reports. No other important planning questions were identified. The extension catalog, raw JSON bundle layout, token storage, and completeness policy are proposals for user approval, not choices the user has already confirmed.
